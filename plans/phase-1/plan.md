## 零、先说人话：这个项目在干什么

**做一个双目测距的小硬件，但它会"偷懒"。**

普通双目测距的做法是：每来一帧画面，就把整张图上每个像素都认认真真算一遍距离。准，但慢、费电。

你的题目是：**先飞快地粗算一遍，只对"算不准"的那几个地方，再花力气精算一遍。**

打个比方。你看一本书的时候，不是每个字都用眼睛最清楚的那一点去盯；你是先扫一眼知道大概，遇到不确定的字才把视线移过去看清楚。人眼本来就是这样工作的——视网膜只有中心一小块是高清的，其余都模糊，靠转头、转眼球来补上。螳螂做立体测距也是这个路子：它只在一个很小的区域里认真算，不是全画面。

所以这个项目有个更直白的名字：**做一个"会看重点"的双目测距模块。**

一句话总结：

> 别人做的是"让双目测得更准"，你做的是"让双目测得更聪明，知道该在哪里使劲"。

### 程序跑起来是这个样子

```
两个摄像头拍照
      │
      ▼
① 粗算：飞快地算一遍，先有个大概
      │
      ▼
② 自查：标出"我这里算不准"的地方
      │
      ▼
③ 精算：只把标出来的地方，换更费力的方法重算
      │
      ▼
  一张深度图（大部分粗算，少数地方精算）
```

## 一、成品长什么样

### 硬件

两个摄像头 + 一块小电脑（树莓派一类）+ 一个功率计（用来测耗电）。

### 程序

就是上面那张图里的三步：粗算 → 自查 → 精算。

### 最后交出去的东西

1. 一个能跑的实物（或一段能演示的视频）
2. 三条曲线（第五节详述）——这是报告的核心证据
3. 一份报告

其中**第二条最重要**。老师能不能看出你做了真东西，主要看那几条曲线。

## 二、整个项目就围绕这一张表

| | 速度 | 耗电 | 精度 |
|---|---|---|---|
| 方案 A：全图都粗算 | 快 | 省 | 差 |
| 方案 B：全图都精算 | 慢 | 费 | 好 |
| **方案 C（你的）：大部分粗算，少数地方精算** | **？** | **？** | **？** |

你要回答的就是那三个问号：

> 方案 C 到底能不能做到"接近 B 的精度、接近 A 的省电"？做不到的话，差在哪？

### 怎么算成功

把 A、B、C 三个方案各测一遍，把结果点画在同一张图上（横轴耗电，纵轴误差）：

- C 落在 A 和 B 连线的**上方** → "偷懒"是划算的，方案成功
- C 正好落在连线上 → 说明自适应没带来额外好处
- C 落在连线**下方** → 说明策略有问题，需要查

**注意：中间那种情况（落在连线上）同样是一个诚实、可写的结论，不算失败。** 能干净地证明"这条路走不通"，也是研究结果。这一点很重要，它决定了你的实验不会因为结果不好而交不出作业。

## 三、给老师看的那一层：认知依据

课程叫"计算机认知基础"，所以报告里必须有一节讲清楚"为什么生物会这么干"。这一层其实很好写，因为证据是现成的：

**人眼不是全画面高清的。** 视网膜上只有中心一小块（中央凹）分辨率最高，其余区域都很模糊。大脑靠不断转动眼球，把中央凹对准当下最需要看清的地方。这叫"主动视觉"。

**螳螂的立体测距只在中央小区有效。** 老师推荐清单里的 Rossel (1983) 证明了昆虫也能用双眼视差测距，而且只在一个很小的捕食区域里做。这直接说明"不做全画面精细测距"是生物界的成熟策略。

**蝗虫用极简的神经回路做实时预警。** Blanchard、Rind 和 Verschure (2000) 把这个回路做进了移动机器人——生物用很少的算力就能完成实时危险判断。

### 对应到学术上的两个名字

| 名字 | 大白话解释 | 在你的项目里对应什么 |
|---|---|---|
| **元认知** | 知道自己"不知道" | 程序自己判断"我这里算得准不准" |
| **注意力资源分配** | 有限的精力投向最需要的地方 | 只把算力花在不可靠的区域 |

这两个都是认知科学里正经的研究题目，不是硬凑的类比。报告开头用它们立论，认知味就足够了。

## 四、三步具体怎么做

### 4.1 第一步：粗算

最简单的做法是用 **OpenCV 自带的 SGBM**（半全局匹配，一种经典的双目测距算法，开箱即用，几行代码就能跑）。如果你的板子算力允许，也可以换成 BANet 这类专门为移动设备设计的轻量神经网络。

这一步的产出：一张大概的深度图。

### 4.2 第二步：怎么知道"哪里算不准"

这是项目里最有技术含量的一步。有四种现成办法，建议前三种都实现，横向比一比哪个更灵——**这本身就是一组完整的实验**。

| 办法 | 大白话解释 | 难度 |
|---|---|---|
| **左右一致性检查** | 把左右两个摄像头的角色调换，重新算一遍。如果一个像素两次算出来的距离对不上，说明这里不可靠 | 极低，OpenCV 自带 |
| **代价曲率** | 算匹配时，如果"最像的位置"和"第二像的位置"差别很小，说明这里没有明确唯一的答案 | 低 |
| **时序一致性** | 连续几帧里，同一个位置的距离值跳来跳去，说明不可靠 | 中 |
| **训练一个小网络** | 专门训练一个模型来预测"这里准不准" | 中高 |

**注意第三种的限制**：如果场景里有东西在动，或者摄像头在动，这个方法就会误判。所以要么在静态场景里用，要么配合光流补偿。

### 4.3 第三步：怎么决定"精修哪些地方"

不要做成"低于某个阈值就精修"这么简单，那样讲不出东西。做成**带预算的挑选**：

> 给每一帧定一个预算，比如"这次最多精修 15% 的像素"。然后按"最不可靠"排序，取最不可靠的那 15% 去精算。

好处有两个：一是实现简单（排序 + 取前 k 个）；二是你可以把预算从 0% 一路扫到 100%，画出**一条曲线**——这条曲线就是整个报告的主图。

"精算"具体做什么？三选一即可：

- 对这一小块区域提高分辨率重新算
- 扩大视差搜索范围重新算
- 换成更强的模型重算

如果板子跑不动深度模型，**用 SGBM 换一组更费时的参数**（更大的搜索范围、更小的块、更高分辨率）也完全算数——它仍然是真实的"多花算力换精度"。

## 五、要测什么数据

三条曲线，外加一个速度数字。术语都给了大白话解释。

### 曲线一：精度-耗电权衡（报告主图）

横轴是"每帧耗多少电"，纵轴是"误差有多大"。把方案 A、B、C 都点上去，看 C 落在哪。

### 曲线二：它说自己不确定的时候，是不是真的算错了

把程序给出的"不可靠程度"分成几档（比如很确定 / 一般 / 很不确定），看看每一档里真正算错的像素占多少。

如果"很不确定"那一档里错误率确实很高，说明**这个程序很懂自己**——这是元认知那一层立论的实证支撑。

标准的做法是画**"风险-覆盖率曲线"**：按不可靠程度排序，保留前面最可靠的一部分像素，看剩下的错误率怎么变。名字听着唬人，实现就是排序加循环，几十行代码。

### 曲线三：每拿到一个可信的深度像素，要花多少电

这个数字最能体现项目的价值。算法是"省电"还是"费电"，看这一个数就够了。

### 速度

帧率也要测。但要注意区分两种延迟：**只算算法本身的时间**，和**从摄像头采集到输出结果的全部时间**。报告里必须写清楚测的是哪一个，两者差距可能很大。

## 六、硬件怎么买

项目里目前没有你手上硬件的记录，所以分了三档。核心设计三档通用，只有"部署与测电"这一章需要按平台调整。

### 档 A：预算最小（约 200–350 元）

- 树莓派 4B（4GB，二手约 200–350 元）或树莓派 Zero 2W
- 两个**同型号** USB 免驱摄像头（约 30–50 元 × 2）
- 测电：USB 功率计（约 30–60 元）

### 档 B：推荐（约 600–900 元）

- 树莓派 5（8GB，约 500–700 元），或你已有的 Linux 开发板
- 两个同型号 USB 摄像头
- 可选：Jetson Orin Nano 作为"高算力对照平台"——同一个策略在不同算力的板子上收益不一样，多这一个平台就多一章实验
- 测电：INA219 / INA226 模块（约 15–30 元），通过 I2C 读取

### 档 C：进阶（后续研究用，本次作业不必完成）

- Tang Nano 20K（约 200 元）：把第一步的粗算部分做成硬件电路，和树莓派组成"硬件 + 软件"的混合系统
- 这一步最适合作为"从作业走向论文"的跳跃

### 买摄像头的三个死规矩

1. **两个必须同型号。** 不同型号的镜头畸变和色彩响应不一样，匹配质量会崩。
2. **必须能手动锁定曝光、增益、白平衡。** 用自动曝光的摄像头，两路画面亮度会一直变，结果完全不可复现。Linux 下用 `v4l2-ctl --set-ctrl` 设置。
3. **基线距离从 6–10 厘米起步。** 基线就是两个摄像头之间的间距：太小则远处测不准，太大则近处有盲区。

**第一条和第二条是踩坑重灾区，务必在买之前确认。**

### 真值从哪来

你需要知道"正确答案"才能算误差：

- **公开数据集**：Middlebury（有高精度真值）、KITTI 2015（室外场景）、ETH3D
- **自己采**：把标定板放在卷尺量好的几个距离上，测系统输出的距离和真实距离差多少。**这是最实用、最容易做好的办法**，强烈建议用它做主要验证。

## 十二、避坑清单

- **摄像头自动曝光是最大的隐形杀手**。必须先锁定参数再采集，否则所有结果不可复现。
- **别在动态场景用帧差或时序方差判断"算不准"**，除非配合光流补偿。
- **测电要分清测的是哪一段**：算法本身，还是从采集到输出的全部。报告里写清楚。
- **先在电脑上把全流程跑通，再搬到板子上**。搬过去遇到的问题，才是嵌入式章节的核心内容。
- **不要追精度排名**。你的贡献是"在约束下的取舍"，不是"测得比谁都准"。
- **别拿白墙、纯色地板做测试**——没有纹理的表面是双目测距的天敌。反过来，"无纹理场景下系统会失效"可以作为报告的一小节。
- **先在电脑上确认"判断算不准"这套东西真的有效**，再去优化嵌入式性能。顺序不要颠倒。
